# DFX 业务流程：模块与一次运行

这是一份约 8 分钟的专题串讲提纲。主线是：**一次运行怎样启用 DFX，各模块在什么位置提供信息，记录怎样变成可查看的结果？** 听完应能说清 DFX 的主要模块、它们的分工，以及一份报告从哪里来。

## 一张图看全程

~~~text
本轮运行配置：选择采集能力与输出位置
  ↓
运行时产生记录
  ├─ 阶段耗时：STRACE / Device phases → 日志或阶段记录
  ├─ 任务、计数、参数、资源：各模块 → 公共采集通道 → Host Collector
  └─ 任务依赖：dep_gen → 设备侧记录后收集，或 Host 构图时直接记录
  ↓
运行结束：收齐尾部记录、核对完整性、导出本轮产物
  ↓
仓库工具：关联记录、转换时间、计算指标
  ↓
阶段耗时 / 任务时间线 / 依赖图 / 计数与资源报告 / 参数内容
  ↓
浏览器、Perfetto 或外部插件查看
~~~

这条链路分成三件事：**运行时留下事实，Host 保存本轮证据，离线工具把证据变成可读结果。** 查看器负责展示已有结果。图中三条记录路径代表不同的事实来源，并不要求所有模块共用同一条采集通道；关键是最终能确认记录属于哪次运行。

讲图时可以把一次运行当作边界：运行前决定要观察什么，运行中只记录当时才能看到的事实，结束时把本轮记录收齐。之后的转换、统计和展示可以重复进行，而不必让运行中的调度承担这些分析工作。

## 模块各自回答什么

- **STRACE / Device phases：** 整轮和主要阶段花了多久。前者主要给出 Host 侧的阶段信息，后者补充设备侧阶段；适合先判断问题落在哪一段。
- **Chip Swimlane：** 任务何时下发、开始和结束。它把视角从“这一轮耗时多少”推进到“哪些任务在执行、哪里出现空档”。
- **dep_gen：** 任务之间有哪些依赖。时间线展示等待发生的时刻，依赖关系帮助解释任务是否必须等待前驱。
- **PMU：** 任务执行时的硬件计数。它为性能分析补充设备侧指标，但计数要结合对应架构和任务上下文解释。
- **Args Dump：** 保存所选任务的参数证据。结果可用于检查输入输出，也能为后续的单任务重放提供材料。
- **Scope Stats：** 记录资源变化与高水位。它帮助判断资源压力或积压是否与异常时间段相伴。
- **Core Swimlane：** 在运行产物的基础上，对单个任务做隔离重放，进一步查看核内执行；它属于后续分析环节。

这些能力回答不同问题。一次运行通常按目的选择其中几项；阶段、任务、依赖、资源和参数等证据可以在落盘后关联。串讲时可以按“先确定阶段，再看任务，再问原因或状态”的顺序介绍，而不是逐个背模块名称。

## 一次运行怎样走完

1. **配置本轮。** 诊断能力首先需要在构建和进程环境中可用，真正启用哪些能力由单次运行配置决定。运行方还指定产物位置，因此连续运行时能够区分每一轮的证据。这里可以强调：看到某个模块存在于程序中，不代表每轮都会采集它的数据。
2. **运行中记录。** Host、AICPU 和 AICore 在各自能观察到事实的位置留下记录。阶段类信息可直接写日志或在结束后读回；持续产生的任务、计数、参数和资源记录经公共采集通道交给 Host。依赖记录按运行时构图方式走设备侧或 Host 侧路径。各模块留下的是不同视角的事实，尚未自动形成统一结论。
3. **收尾并导出。** Host 收到记录后按模块整理，有些产物在运行中已经开始写入。结束时仍需停止产生新记录、收齐尾部数据、核对采集与丢弃情况，再完成本轮原始产物。如果少了尾部或存在丢弃，后续看到的空白就可能是采集缺口，不能直接解释为任务没有运行。
4. **离线处理。** 仓库工具把原始记录关联到任务、换算时间或汇总指标，得到时间线、依赖图和统计结果。例如，任务时间记录要经过关联才适合画泳道；时间线与依赖关系合用，才能进一步讨论任务空档。原始记录与最终视图是两个阶段。
5. **查看结果。** 日志和统计表适合看阶段或指标，时间线适合看先后关系，依赖图适合看任务约束；仓库生成的报告可在浏览器打开，转换后的时间线也可交给 Perfetto 或外部插件。图表呈现证据，查看器本身不负责运行时采集。

## 用一个慢运行串起全程

假设同一场景的运行时间变长。第一步看阶段耗时：如果主要增长发生在设备执行阶段，再打开任务时间线。时间线可能显示某些任务本身变长，也可能显示任务之间有明显空档；这两种现象指向不同的下一步。任务本身变长时，可再看对应硬件计数；空档明显时，结合依赖关系判断后继任务是否尚未就绪，必要时再看资源水位。每增加一类证据，都是为了回答前一张图留下的具体问题。

这个例子也说明产物之间的关系：阶段记录负责缩小范围，泳道负责定位时间，依赖、计数和资源记录负责解释可能的约束。最后应回到原始运行，确认这些记录完整且属于可比的场景，才把观察提升为性能判断。

## 建议讲述节奏

- **0:00–1:00：** 从“一次运行会留下什么”切入，展示总图。说明配置、记录、落盘、分析、查看是连续链路。
- **1:00–2:30：** 介绍模块分工。按阶段、任务、依赖、计数、参数和资源六类问题讲，最后点出 Core Swimlane 是单任务的后续分析。
- **2:30–4:30：** 顺着运行讲配置、Host / Device 记录和不同采集路径，重点解释公共采集通道与直接记录路径最终如何汇合到本轮产物。
- **4:30–5:45：** 讲结束时的收尾和完整性核对，再讲原始产物为什么要经过离线关联与转换。
- **5:45–7:15：** 用上面的慢运行例子，把阶段、任务时间线、依赖和资源证据接起来。
- **7:15–8:00：** 回到总图收束：每个模块只提供一种事实，可信的解释来自同一运行中可对照的证据。

需要继续深入某个模块时，可从 [DFX 框架总览](../总览/DFX框架总览.md) 查实现链路；[芯片泳道任务时间线](芯片泳道任务时间线.md) 展开了其中一条专题。
