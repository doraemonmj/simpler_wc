# DFX 业务流程与模块总览

## 背景与目标：为什么需要 DFX

simpler 的一次执行跨越 Host、AICPU 和 AICore。Host 负责准备和发起运行，AICPU 组织任务与依赖，AICore 执行计算。运行变慢、卡住或结果异常时，单看总耗时或最终报错，通常无法判断问题发生在哪一层：可能是准备阶段变长、任务等待依赖、设备资源紧张，也可能是某个任务本身执行变慢。

**DFX 是贯穿一次运行的诊断与性能观测能力。** 它让不同位置在运行时留下各自掌握的事实，由 Host 汇集本轮记录，再通过离线工具整理成阶段耗时、任务时间线、依赖关系和报告。DFX 的目标不是在运行中直接给出一个“根因”，而是提供一条可追溯的证据链：**先定位变慢或出错的阶段，再缩小到任务和约束，最后用多种记录互相验证。**

这条业务流程需要解决三个实际问题：

1. **证据分散：** 阶段、任务、依赖、资源和硬件指标产生于不同位置，需要归到同一次运行。
2. **采集有代价：** 不同问题需要的细节不同，应按本轮诊断目的选择能力，避免无谓开销。
3. **记录需要解释：** 原始时间戳或计数只描述现象；还要收齐尾部、核对缺失、对齐时间并关联任务，才能形成可信结论。

## 从哪里开始，什么时候结束

一次 DFX 流程通常由两类需求触发：日常观察一轮运行的阶段耗时，或针对慢、卡、错等现象做专项诊断。诊断者先确定要回答的问题和可对比的运行，再选择本轮可用的采集能力。构建开关决定某些能力是否存在，进程环境会影响日志输出，单次运行配置决定本轮开启哪些专项采集和产物位置。因此，“开启 DFX”不是一个对所有模块都相同的总开关。

流程的输入是**待观察的工作负载、本轮运行配置和诊断问题**；有性能比较需求时，还要有同口径的基线。流程在原始记录完成收尾、所需视图生成，并能说明结论及证据边界时结束。若运行异常中断或记录丢失，仍应保留可用事实，但结论必须说明缺口。

## 总体框架：谁负责哪一段

从业务职责看，可以把 DFX 分成四段：

| 环节 | 主要职责 | 交给下一环节的内容 |
| ---- | -------- | ------------------ |
| 控制与准备 | 选择本轮采集、校验配置、准备输出和采集资源 | 启用状态与可写入的采集通道 |
| 运行时记录 | Host、AICPU、AICore 在事实产生处记录阶段、任务、依赖和指标 | 带本轮归属的原始记录 |
| Host 收集与收尾 | 接收设备记录、保存产物、排空尾部并核对完整性 | 本轮原始产物及采集状态 |
| 离线分析与查看 | 关联任务、转换时间、汇总统计并展示 | 可用于定位和解释的视图与报告 |

功能模块决定**记录什么**。公共 Profiling Framework 与 Host Collector 承接需要持续传递的设备记录；STRACE 使用日志路径，Device phases 使用固定阶段记录，Host 构图时的 dep_gen 也可以直接留下依赖。这些记录最后按同一轮运行汇合，并不要求走同一个 Collector。

~~~mermaid
flowchart LR
    A["诊断问题与本轮配置"] --> B["准备与初始化"]
    B --> C["Host / AICPU / AICore 运行并记录"]
    C --> D["Host 收集与收尾"]
    D --> E["本轮原始产物"]
    E --> F["离线关联、转换、统计"]
    F --> G["时间线 / 依赖图 / 报告"]
    G --> H["对照问题形成结论"]
~~~

### 各模块回答什么问题

| 模块 | 主要观察内容 | 典型用途 |
| ---- | ------------ | -------- |
| STRACE / Device phases | Host 与设备运行阶段及耗时 | 先判断时间花在哪一段 |
| Chip Swimlane | 任务下发、开始和结束的时间 | 看任务是否并行、哪里出现空档 |
| dep_gen | 任务间依赖 | 判断空档是否由前驱未完成造成 |
| PMU | 任务执行时的硬件计数 | 解释计算任务执行变慢的线索 |
| Scope Stats | 范围内的资源用量和高水位 | 观察容量压力或积压 |
| Args Dump | 所选任务的参数内容 | 检查输入，支持后续单任务分析 |
| Core Swimlane | 单任务隔离重放后的核内时间线 | 在运行后继续追查某个任务 |

Core Swimlane 是使用已有材料做进一步重放分析，不属于每轮正常运行都会开启的整轮采集。其他模块也按诊断需要选择，不要求同时开启。

## 主流程：从触发到形成结论

### 1. 明确问题，选择观察范围

触发点可能是“这一轮比基线慢”，也可能是卡住、报错或需要例行记录。先明确要比较的场景、运行轮次和指标：如果只想知道 Host 与设备各用了多久，阶段记录通常是起点；如果需要追到任务等待，则增加 Chip Swimlane 和依赖信息；如果怀疑任务本身或资源问题，再选择 PMU、Scope Stats 或 Args Dump。这个选择决定后续会有什么证据，也决定观测开销。

### 2. 配置本轮，确认产物归属

Host 读取并校验本轮配置，确认请求的能力在当前构建中可用，确定输出位置，并让日志、专项采集与运行轮次对应。性能对比还应保持工作负载、运行条件和采集范围尽量一致；否则两份时间线的差异可能来自配置，而非代码行为。

### 3. 初始化采集，再启动执行

Host 为启用的模块准备采集资源和输出。需要连续接收设备记录的 Collector 建立接收能力并在设备执行前启动；启用状态传递给设备侧，使记录行为与本轮配置一致。STRACE、Device phases 等按各自路径准备。初始化的结果是“这轮可以记录哪些事实”，此时还没有性能结论。

### 4. 运行过程中，在事实产生处记录

工作负载执行时，Host 留下运行阶段，AICPU 侧记录调度、依赖、资源或参数等事实，AICore 侧提供任务执行时间及可选的硬件计数。同一个任务可能同时出现在泳道、依赖和计数记录中；每个模块只描述自己看到的那一面。例如，泳道中的等待空档是现象，依赖记录才能帮助判断它是否必须等待前驱。

### 5. Host 持续收集并保存

需要持续传递的设备记录通过公共 Profiling Framework 交给对应的 Host Collector；日志、固定阶段记录和 Host 直接生成的数据走各自的保存路径。有些原始产物在运行中已经开始落盘。此时应把它们视为一轮执行的分散证据，而不是已完成的报告。

### 6. 停止、排空和核对本轮记录

执行结束后，停止产生新记录，收齐仍在途中的尾部，再完成各模块的输出和资源释放。收尾时核对产生、接收及丢弃等采集状态，确认哪些数据完整、哪些可能缺失。运行中断时尤其要把“程序没有完成”与“记录没有收齐”分开说明，避免把图中的空白误判为设备空闲。

### 7. 离线加工，生成可读视图

分析工具读取本轮原始产物：把阶段标记汇总成耗时，把任务记录关联并转换时间，按依赖关系组织任务图，并整理资源、计数或参数报告。时间线中的不同来源需要按工具规则对齐，不能仅凭两个原始时间戳直接比较。浏览器、Perfetto 或外部查看器负责展示结果；它们消费的是已经采集和转换的数据。

### 8. 对照问题解释结果，结束本轮分析

先回到最初的问题：慢在准备、调度等待，还是任务执行？再用第二类证据验证初步判断。例如，阶段耗时锁定设备段，泳道发现任务间空档，依赖图解释等待，资源记录进一步检查是否有容量压力。最后记录结论、对应的运行和产物，以及采集缺口或对比条件的限制。若证据不足，就据此决定下一轮要补充哪类采集；这会开启新的诊断轮次。

## 最终能得到什么

一轮 DFX 的交付物分为两层：**原始产物**保存阶段日志、泳道记录、依赖数据、计数、资源或参数等事实；**分析视图**把这些事实组织成耗时表、时间线、依赖图和报告。前者让结论可以复查，后者让问题更容易定位。没有开启的模块不会凭空产生对应产物，记录丢失也不能靠可视化补回来。

例如，一轮运行变慢时，读者可以沿着“阶段耗时 → 任务时间线 → 依赖与资源 → 具体任务指标”的顺序逐步缩小范围。这也是整套流程的价值：从一次运行中的分散观察，得到可以解释、比较和复查的结论。
