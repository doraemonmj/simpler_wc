# DFX 业务流程：从异常到验证

DFX 围绕一次具体运行建立证据链。它的业务目标是让开发者从“哪里不对”走到“问题落在哪个阶段或任务、下一步该查什么”，再用同一场景验证处理结果。

## 主流程

~~~text
发现异常并明确问题
  → 选择要观察的事实
  → 带采集配置复现运行
  → 核对本轮产物
  → 整理和查看证据
  → 缩小问题范围并形成判断
  → 修改后在可比条件下复验
~~~

1. **明确问题。** 记录运行场景、预期与实际差异，以及正常运行的参照。先区分结果错误、卡住、耗时变长和资源压力，避免一开始就收集所有数据。
2. **选择证据。** 根据问题决定观察粒度：先看整轮和阶段，再按需看任务时间、等待关系、资源、硬件计数或参数。采集范围越贴近问题，结论越容易解释。
3. **复现并产出记录。** 为这次运行启用所需的 DFX 能力。运行中的事实被记录并归入本轮；结束后形成日志、原始记录或统计产物。
4. **核对证据。** 确认产物属于同一轮、记录完整，且跨来源的时间能正确对齐。若采集影响了运行速度，应把这种影响纳入解释。
5. **整理与查看。** 将原始产物变成阶段耗时、任务时间线、依赖关系或统计视图。从整体异常逐步缩小到相关阶段、任务或资源，再用其他证据验证推断。
6. **形成结论并复验。** 说清观察到的事实、推断的原因和仍有的疑点。处理后用可比的场景再次运行，检查现象和关键指标是否改变。

## 不同问题的入口

- **运行变慢：** 先找变长的阶段，再看相关任务的执行与空档；需要解释等待时，再结合依赖关系。
- **运行卡住：** 先确认最后的进展和停住的位置，再看相关任务、等待关系或资源状态。
- **结果错误：** 先确定从哪一步开始偏离预期，再查看对应任务的输入、输出和必要的单任务证据。
- **资源压力：** 先看资源变化与异常发生的时间范围，再关联到相关阶段和任务。

最终交付的是一个可复核的判断：问题出现在哪次运行、哪段流程，有什么证据支持，以及复验结果如何。某张图上的空白或单个计数通常只是线索，需要放回这条证据链中解释。
