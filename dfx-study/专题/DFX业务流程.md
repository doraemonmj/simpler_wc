# DFX 总览：设计逻辑、组件与运行流程

## 1. DFX 是什么

### 1.1 背景：为什么需要 DFX

simpler 的一次运行跨越 Host、AICPU 和 AICore：Host 准备并发起执行，AICPU 组织任务，AICore 完成计算。最终耗时和返回结果只能告诉我们“这一轮怎么样”，无法单独说明“时间花在哪里”或“异常从哪里开始”。同样是运行变慢，原因可能在 Host 准备、设备调度、任务等待，也可能在任务执行本身。

这些信息分散在不同执行层和不同时间点。如果只看某一处日志，很容易把现象当成原因：例如时间线上的空档说明任务没有执行，却不能独自说明它在等待依赖、等待资源，还是没有被及时下发。因此需要一套贯穿本轮运行的观测能力，把阶段、任务及相关状态放到同一条证据链上。

| 遇到的现象 | 首先要回答的问题 |
| ---------- | ---------------- |
| 整轮耗时增加 | 增长发生在 Host 准备、设备调度，还是计算阶段？ |
| 任务之间出现空档 | 任务受依赖约束，还是调度或资源没有跟上？ |
| 某个任务异常或变慢 | 任务参数、硬件指标和执行细节有什么变化？ |

### 1.2 定位与目标：DFX 要解决什么问题

本文中的 DFX 指 simpler 围绕一次运行提供的诊断与性能观测能力。它在事实产生的位置留下记录，按本轮运行汇集原始产物，再通过分析工具把记录组织成阶段耗时、任务时间线、依赖关系和资源等视图。

DFX 希望支持一个由粗到细的判断过程：**先确认异常是否存在及其范围，再定位到阶段或任务，最后结合其他证据解释原因。** 对日常观测，它提供可比较的运行画像；对专项诊断，它帮助开发者决定下一步该检查哪里、还需要补充什么数据。最终交付的不只是图或日志，而是能够指向某次运行、可以复查其依据的结论。

原始记录和分析结论是两回事。记录描述“发生了什么”，结论还需要关联不同来源、核对采集完整性，并结合工作负载与对照运行来解释；看到一个耗时峰值或空档，并不自动等于找到了根因。

### 1.3 使用场景与能力边界

DFX 适合在两类情况下使用：一是持续观察运行的整体阶段耗时，发现与基线不同的轮次；二是在性能下降、执行卡住、资源紧张或结果异常时，按问题选择更细的任务、依赖、计数或参数记录。通常先用低开销的整体信息缩小范围，再决定是否进行更细的采集或单任务分析。

它有三个边界需要先说明：

- **并非所有能力每轮都可用。** 一部分能力取决于构建或进程环境，专项采集还取决于本轮配置；没有开启的记录无法在运行后补出。
- **观测会影响被观测对象。** 更细的采集可能增加运行开销。比较两轮性能时，需要关注工作负载、运行条件和采集范围是否一致。
- **证据有完整性和解释条件。** 异常中断、记录丢失或不同来源的时间尚未对齐时，视图只能支持有限判断。DFX 提供定位依据，不会代替故障处理，也不能单凭一张图证明根因。
