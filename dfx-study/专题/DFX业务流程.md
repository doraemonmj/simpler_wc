# DFX 业务流程与模块总览

## DFX 是什么

DFX 是 simpler 随一次运行提供的诊断与性能观测能力。当结果错误、执行卡住、耗时增加或资源紧张时，开发者需要知道问题出现在哪里。程序执行时，Host、AICPU 和 AICore 各自知道一部分事实：某个阶段用了多久、任务何时被下发和执行、任务之间有什么依赖、资源和硬件计数怎样变化。DFX 把这些事实按运行轮次留下来，再整理成时间线、依赖图和报告，帮助开发者从现象追到具体阶段或任务。

一份 DFX 结果有两个层次：**原始产物记录发生了什么，分析视图帮助解释这些记录。** 例如，任务时间记录可以画出泳道，但泳道中的空档需要结合依赖或资源信息才能解释。理解这两个层次，就能知道各模块为何分工，以及为什么采集完成后还要做离线分析。

## 设计时考虑什么

- **在事实产生的位置记录。** Host 知道运行阶段，调度侧知道下发、依赖和资源状态，计算侧知道任务执行时间与硬件计数。把这些视角合起来，才能从整轮耗时逐步缩小到任务。
- **按本轮问题选择采集。** 诊断能力可能需要构建开关，进程环境也会影响日志输出；单次运行配置决定本轮真正开启哪些采集能力和产物位置。采得越细，观察运行所付出的代价通常越高。
- **先保证证据可信。** 每份记录需要有明确的运行归属；结束时要收齐尾部并核对缺失或丢弃。不同来源的时间还可能需要换算和对齐。否则图上的空白或时间差未必反映真实执行。

这三点决定了整体做法：运行时尽量留下必要事实，Host 负责把本轮记录收齐，关联、计算和展示主要放到运行之后。

## 总体框架

从职责看，DFX 可以分成四层：

1. **控制与准备：** 接收本轮配置，确定启用的模块和输出位置，准备采集所需资源。
2. **运行时记录：** 各模块在 Host、AICPU、AICore 上记录自己掌握的阶段、任务、依赖、计数、资源或参数事实。
3. **Host 收集与落盘：** 把设备记录交给对应 Collector，结束时排空和对账，形成属于本轮的原始产物。
4. **离线分析与查看：** 仓库工具关联、转换和统计产物，浏览器或外部查看器呈现最终视图。

其中，**功能模块决定记录什么，公共 Profiling Framework 与 Host Collector 负责持续记录的交接和保存**。STRACE 与 Device phases 使用日志或固定阶段记录；dep_gen 在设备侧构图和 Host 构图时也有不同路径，因此所有记录并不强行经过同一条通道。

## 子模块分别回答什么

- **STRACE / Device phases：** 查看 Host 和设备的阶段耗时，先回答“时间主要花在哪一段”。
- **Chip Swimlane：** 记录任务下发、开始、结束的时间，回答“哪些任务在运行，哪里有空档”。
- **dep_gen：** 记录任务之间的依赖，帮助判断后继任务是否必须等待前驱。
- **PMU：** 提供任务执行时的硬件计数，补充设备侧性能指标。
- **Scope Stats：** 提供资源变化与高水位，帮助判断容量压力和积压。
- **Args Dump：** 留下所选任务的参数内容，供结果检查或后续重放。
- **Core Swimlane：** 使用已有材料隔离重放单个任务，查看更细的核内时间线；它属于运行后的进一步分析。

这些模块不要求每轮一起开启。阶段和任务时间负责定位位置，依赖、计数、资源和参数用于解释已经看到的现象。

## 一次运行的生命周期

### 初始化：让本轮具备采集条件

初始化先回答“这轮要收什么”。运行配置被校验后，Host 为启用的模块准备输出位置和采集资源；需要持续接收设备记录的 Collector 会建立对应的接收能力，并在设备运行前开始工作。启用状态也要传给设备侧，使实际记录与本轮配置一致。

这一步不等于把所有 DFX 模块都打开。未启用的模块不会产生对应产物；STRACE、Device phases 等阶段信息与持续记录的 Collector 路径也不同。把准备工作限定在本轮，连续执行多轮时才能分别管理各轮记录。

### 运行中：模块记录，Host 收集

运行开始后，Host、AICPU 和 AICore 在各自掌握事实的位置记录。Host 侧留下运行阶段，调度侧知道任务下发、依赖、参数和资源状态，计算侧能够提供任务执行时间与硬件计数。同一个任务因此可能在多个模块中出现，但各模块只记录自己的观察结果。

持续产生的设备记录通过公共 Profiling Framework 交给 Host 的各模块 Collector。Collector 按记录类型整理数据，有些内容在运行中已开始写盘。阶段记录和 Host 直接形成的依赖数据按各自路径保存。此时得到的是分散的事实，还没有自动形成“为什么慢”的结论。

### 收尾：形成可信的原始产物

运行结束时，先停止产生新记录，再收齐仍在途中的尾部数据，核对采集量与丢弃量，最后完成本轮产物。常见产物包括阶段日志、泳道原始记录、依赖数据、PMU 计数、资源记录和参数数据。若本轮记录不完整，后续分析必须带着这个边界解读。

### 离线分析与查看

离线工具再把这些原始产物变成方便阅读的结果：阶段日志可汇总为耗时表；泳道记录需要按任务关联并转换时间；依赖数据可以形成任务关系图；资源和参数记录可以生成报告或用于单任务检查。Perfetto、浏览器或外部插件负责查看相应结果，采集和转换仍由 simpler 侧完成。

## 一个例子：怎样把几类证据串起来

以“同一场景运行变慢”为例，先用阶段耗时确定增长段，再用 Chip Swimlane 判断是任务执行变长还是任务间空档。前者可结合 PMU 看任务指标，后者需结合依赖关系、资源记录判断约束。最终要回到本轮产物的完整性和对照运行的可比性，才能把几张图串成可信的解释。
