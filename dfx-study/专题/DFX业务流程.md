# DFX 业务流程：一次运行怎样留下可读结果

这份专题介绍 DFX 随一次 simpler 运行怎样工作。重点是整体链路和模块分工：运行前决定采什么，运行中留下事实，结束时收齐本轮记录，运行后再把记录整理成可查看的结果。

## 先建立整体框架

可以把 DFX 分成四层：**控制、记录、归集、分析与展示**。控制层决定本轮开启哪些能力、产物写到哪里；记录层在 Host 和设备上捕捉各自能看到的事实；归集层把记录保存为属于本轮的产物；分析与展示层把原始记录转换为时间线、依赖图和报告。

各模块按观察对象分工，并非全部首尾相接。阶段耗时、任务时间、依赖、硬件计数、资源和参数可以单独采集，也可以在落盘后互相印证。理解这点，后面就容易分清“运行时记录了什么”和“图表后来计算出了什么”。

## 模块怎样分工

- **看时间：** STRACE 和 Device phases 给出 Host、设备的阶段耗时；Chip Swimlane 再把视角推进到任务，展示下发、执行和完成的时间关系。
- **看任务关系：** dep_gen 给出依赖边。泳道上的空档说明当时没有可见任务在执行，依赖关系则帮助判断后继任务是否还在等前驱。
- **看执行状态：** PMU 提供任务对应的硬件计数；Scope Stats 展示资源变化和高水位。它们帮助解释性能现象，但计数和水位仍需放回具体任务、阶段中解读。
- **看任务内容：** Args Dump 留下所选任务的参数证据。需要再深入单个任务时，Core Swimlane 可以利用已有材料做隔离重放；这一步发生在整轮运行之后。

这里可以用一句话串起来：**先用阶段和任务时间定位位置，再按问题补依赖、状态或参数证据。**

## 一次运行怎样走通

**运行前，配置本轮。** 诊断能力需要先在构建和进程环境中可用；单次运行配置决定这轮真正启用哪些能力和输出位置。因此，不是每轮都会产生所有 DFX 产物。讲述时可以把“本轮”作为边界：连续运行也要能认出每份记录属于哪一次。

**运行中，各处记录事实。** Host 侧能够记录运行阶段，调度侧知道任务下发、依赖和资源状态，计算侧能够记录任务执行时间及硬件计数。阶段类信息可进入日志或在结束后读回；持续产生的任务、计数、参数和资源记录经公共采集通道交给 Host。dep_gen 则随构图方式走设备侧采集或 Host 直接记录。

**运行结束，形成可靠产物。** Host 收集各类记录，部分文件可能在运行中已开始写入；结束时仍要收齐尾部、核对采集与丢弃情况，再完成导出。记录缺失时，图上的空白未必代表设备空闲。原始产物先回答“发生了什么”，还不是最终的分析视图。

**运行后，整理并查看。** 仓库工具关联同一任务的记录、换算时间或汇总指标，生成时间线、依赖图和统计报告。浏览器、Perfetto 或外部插件负责展示这些结果。采集、整理和展示分开，既能保留原始证据，也能从同一份产物提出不同问题。

下面的图用于讲完四个环节后，再沿箭头回顾一次：

    CFG["本轮配置<br/>能力、输出位置"] --> RUN["一次运行"]

    DEP --> FINAL
    FINAL --> RAW["本轮原始产物"]
    RAW --> TOOL["离线关联与统计"]
    TOOL --> VIEW["时间线、依赖图、报告"]
~~~

## 用慢运行说明结果怎么配合

假设同一场景比以前慢，先看阶段耗时，确定增长发生在 Host、设备执行还是其他阶段。若设备执行段增长，再看任务时间线：是某些任务条变长，还是任务之间出现空档？前者可以结合 PMU 看任务指标；后者需要结合依赖关系和资源记录，判断任务是否已经具备执行条件。每一类视图回答一个问题，并引出下一类证据。

最后核对本轮记录是否完整、对照运行是否可比，以及采集对耗时的影响。这样形成的结论，才有清楚的证据路径。

## 约 8 分钟的讲述安排

- **0:00–1:15：** 用四层框架解释 DFX 的输入、过程和输出。
- **1:15–3:15：** 按时间、关系、状态、内容讲模块分工。
- **3:15–6:00：** 顺着一次运行讲配置、记录、收尾、离线整理；最后用图回顾。
- **6:00–7:30：** 用慢运行例子串联几类结果。
- **7:30–8:00：** 收束到“本轮事实 → 可靠产物 → 可解释视图”。
