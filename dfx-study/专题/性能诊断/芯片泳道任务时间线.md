# Chip Swimlane：任务时间线

Chip Swimlane 用于观察一轮运行中各任务的下发、执行和完成情况。当运行变慢时，它帮助区分耗时落在核上执行、下发后等待，还是任务之间的空档。整体 DFX 链路见[DFX 业务流程](../../总览/DFX业务流程.md)。

详细字段及不同 runtime、架构的差异见[原设计文档](../../../docs/dfx/chip-swimlane-profiling.md)。

## 1. 设计逻辑

一条任务时间线需要两个位置的记录：AICore 知道任务在核上何时开始、结束；调度侧知道任务何时下发、何时完成。两侧在运行时只记录各自掌握的事实，减少在线处理；任务关联、时间换算和视图生成放到落盘后完成。

采集按所需信息分层开启。级别 1 记录 AICore 的任务时间；级别 2 增加调度侧的逐任务下发、完成时间；级别 3 增加调度阶段；级别 4 再增加任务提交阶段。`--enable-chip-swimlane` 裸开关默认级别 4。任务依赖不由泳道采集，而由 dep_gen 单独生成 `deps.json`，供离线分析时关联。

## 2. 运行时怎样形成记录

| 采集位置 | 采集点与数据 | 为什么需要 |
| -------- | ------------ | ---------- |
| AICore 执行器 | 任务取到后，在核函数执行前后记录时间、任务标识、核编号和每核下发序号 | 只有执行核能界定真正的核上执行窗口。 |
| Scheduler | 下发任务、开始处理完成通知时记录时间及同一个每核下发序号 | 与 AICore 时间配对，拆开下发等待、核上执行和完成通知间隔。Scheduler 可能在 AICPU 或 AICore。 |
| Scheduler 循环 | 级别 3 起记录各调度阶段的起止周期、类别及调度器身份 | 解释任务之间的空档是否对应调度工作；阶段类别由 runtime 决定。 |
| Orchestrator | 级别 4 起记录任务提交或张量分配调用的起止时间 | 找出哪个提交慢；T&R 在 AICPU 采，HBG 在 Host 采。 |

实现入口可从 [AICore 执行器](../../../src/a2a3/runtime/tensormap_and_ringbuffer/aicore/aicore_executor.cpp)与 [AICPU 写入接口](../../../src/common/platform/include/aicpu/chip_swimlane_collector_aicpu.h)查起。

```text
本轮启用 Chip Swimlane
    ├─ AICore 记录任务开始、结束时间
    └─ 调度侧记录任务下发、完成时间；按级别记录调度和提交阶段
             ↓
公共 Profiling Framework 交接设备缓冲
             ↓
Host Collector 按运行和记录类型收集、核对
             ↓
chip_swimlane_records.json（尚未按任务关联的原始记录）
```

公共框架负责缓冲轮转、Host 接收和回收；Collector 在运行结束时排空记录、核对采集与丢弃计数，再导出原始文件。AICore 和调度侧的记录仍分别保存，避免在设备运行路径中做复杂分析。交接机制见[DFX 采集与落盘](../采集与落盘/DFX采集与落盘.md)。

## 3. 原始记录怎样变成时间线

`swimlane_converter.py` 读取 `chip_swimlane_records.json`，关联同一任务的 AICore 与调度侧记录，将设备周期换算成时间，并生成可在 Perfetto 中查看的 `merged_swimlane.json`。若有匹配的 `deps.json`，转换器还能加入依赖箭头；再配合 `name_map*.json` 可显示内核名称。

原始文件中，AICore 的 `aicore_tasks` 保留任务标识、核编号、每核下发序号、开始/结束周期及 `run_epoch`；Scheduler 的 `scheduler_tasks` 保留同一核与序号上的下发/完成周期及 `run_epoch`。转换器按 `(run_epoch, core_id, 每核下发序号)` 配对：一个任务可能在同一核多次下发，单用任务 ID 会误配。`metadata.clock_freq_hz` 用于把周期换为微秒；`start_time_us` 等是离线计算结果，不是设备直接采集字段。

```text
调度侧下发          AICore 开始          AICore 结束          调度侧完成
   dispatch ────────── start ───────────── end ───────────── finish
       下发到开始的间隔       核上执行时间        结束到完成的间隔
```

`start → end` 表示核上执行时间；`dispatch → start` 表示下发到核开始执行的间隔。任务条之间的空档只说明这段时间没有可见的任务执行。要判断空档是否由依赖或调度造成，还需结合 `deps.json`、调度阶段记录等证据；`sched_overhead_analysis.py` 和 `critical_path.py` 可进一步分析调度开销与关键路径。

## 4. 结果的适用边界

- 级别 1 没有调度侧的下发、完成时间，不能仅凭它分析下发后的等待。
- 泳道记录本身没有依赖边；没有 `deps.json` 时，仍能看任务时间，但无法据此判断前驱约束。
- dep_gen 采集可能影响提交时序。分析调度开销时，通常将同一计算图另一轮运行的依赖图与计时记录配合使用。
- 采集可能扰动耗时；若记录丢失或本轮数据不完整，应先核对证据质量。
