# PyPTO 3.0 IDE 输入数据结构

这里按“打开哪个文件、插件从中读什么”列出 PyPTO 3.0 主线。依据是本机扩展 `cann-pub.pypto-toolkit-4.0.36` 的 `dist/` 与 `.d.ts`、`pypto-tools_public/docs/zh/`，以及 simpler 当前导出样例。字段表描述当前读取路径，不是对所有版本的通用 schema 保证。

## 文件组合

```text
dfx_outputs/
├── chip_swimlane_records.json    # 芯片任务原始记录；可直接打开
├── deps.json                     # 任务图；可直接打开，亦增强泳道
├── name_map_<timestamp>.json     # 函数名；结合泳道生成性能表
├── CPM_static.json               # 可选，静态关键路径高亮
└── CPM_observed.json             # 可选，观测关键路径高亮

passes_dump_<timestamp>/
├── 00_frontend.py
├── 01_<Pass>.py
├── 01_<Pass>.log                 # 可选 warning
├── 02_<Pass>.py
└── NN_after_AllocateMemoryAddr.py # 符合命名时可做 Memory Map

serving-strace-swimlane.json      # Serving 独立时间线
```

这些文件可分开产生；只有 Chip Swimlane 主文件就能尝试看任务时间，依赖、函数名与关键路径需要额外文件。PyPTO 3.0 的这些直接打开路径不要求先生成旧插件侧边栏用的 `rundata.json`。

## Chip Swimlane 原始记录

本机扩展 `dist/converter/perfSwimlaneConverter.d.ts::RawSwimlaneRecords` 将顶层 `aicore_tasks[]` 作为原始格式特征，`metadata.clock_freq_hz`、`num_cores`、`core_types[]` 用于时间换算及 Core 类型。simpler 当前七列行格式由 `tests/ut/cpp/common/platform/test_chip_swimlane_run_export.cpp` 和 `simpler_setup/tools/swimlane_converter.py` 定义：

```text
aicore_tasks[] = [core_id, task_token, reg_task_id,
                  start_cycles, end_cycles, receive_to_start_cycles, run_epoch]

scheduler_tasks.records[] = [core_id, reg_task_id,
                             dispatch_cycles, finish_cycles, run_epoch]
```

| 顶层字段 | 内容 |
| -------- | ---- |
| `chip_swimlane_level` | 本轮采集级别，影响可见的视图 |
| `metadata.clock_freq_hz` | device cycle 转微秒的频率 |
| `metadata.num_cores`、`metadata.core_types`、`metadata.core_to_thread` | Core 数量、类型及 Scheduler 线程映射 |
| `aicore_tasks` | Worker 执行区间与任务标识 |
| `scheduler_tasks` | 当前 simpler 的 dispatch / finish 记录 |
| `scheduler_records.streams` | 当前 simpler 的 Scheduler 阶段，记录 `kind`、`start_cycles`、`end_cycles` 等 |
| `aicpu_orchestrator_phases`、`host_orchestrator_phases` | 不同运行时的编排阶段 |

当前 simpler 对同一 `reg_task_id` 的多轮运行用 `run_epoch` 区分。**本机扩展 4.0.36 的转换器仍从 `aicpu_tasks`、`aicpu_scheduler_phases` 读取旧式调度数据，AICore join 未使用 `run_epoch`。** 因此上表是当前 simpler 产物形状，同时也标明了与该安装包的兼容边界；不能把插件的基础格式验证当作完整兼容证明。

该扩展还接受较早的顶层 `tasks[]` 微秒域格式，每条任务含 `task_id`、`func_id`、`core_id`、`core_type`、`ring_id`、`start_time_us`、`end_time_us` 等。`merged_swimlane.json` 则是另一种顶层 `traceEvents[]` 的已转换格式；同目录有 chip 原始文件时，本机插件预览优先转向 chip 文件。

## `deps.json` 任务图

`dist/core/deps-graph/depsGraph.types.d.ts::DepsJsonData` 声明顶层 `edges[]`，可带 `tasks[]`、`tensors[]`。`dist/core/deps-graph/depsGraphBuilder.js` 以边端点 `pred`、`succ` 建图，并用任务和 Tensor 表增强节点。示意：

```json
{
  "tasks": [
    { "task_id": "1", "kernel_ids": [7, -1, -1], "block_num": 1 },
    { "task_id": "2", "kernel_ids": [-1, 8, -1], "block_num": 1 }
  ],
  "edges": [
    { "pred": "1", "succ": "2", "source": "explicit" }
  ],
  "tensors": []
}
```

`tasks[].args[]` 可含 `idx`、`type`、`tensor_id`、`dtype`、`shape`、`strides`、`start_offset`；`tensors[]` 可含 `tensor_id`、`name`、`dtype`、`shape`。`tasks[].kernel_ids` 还用于 Chip Swimlane 恢复 Func ID。生产者需要保持任务 ID 在记录、边和任务表之间一致；大整数的 JSON/JavaScript 精度边界应在实测中核对。

## `name_map*.json` 与 CPM

名称映射的关键字段是：

```json
{ "callable_id_to_name": { "7": "kernel_a", "8": "kernel_b" } }
```

`nameMapTable` 还要求同目录有受支持的泳道文件，用任务时间计算 Count、Max、Min、Avg；单独的映射表不能产生耗时。Chip Swimlane 会把 `deps.json` 的 `kernel_ids` 与 `callable_id_to_name` 联起来显示名称。

`CPM_static*.json` 与 `CPM_observed*.json` 是辅助 trace。`dist/handler/swimGraphMsgHandler.js::getCriticalPathData` 读取其中的 `traceEvents[]`，选取 `ph: "X"`、`pid: 4` 的 Worker 事件，并取 `args.taskId` 做高亮。没有 CPM 不妨碍基础泳道打开。

## IR Pass 快照与 Memory Map

`dist/services/ir-trace/discovery.js` 要求目录中存在 `00_frontend.py`；后续 `.py` 文件名匹配 `NN_<PassName>.py`，索引从 1 连续递增，不允许缺号或重复。同名 `.log` 可选。输入内容是每个 Pass 后的 Python IR 文本，插件比较相邻快照，不要求额外 JSON schema。

Memory Map 读取匹配 `*after_AllocateMemoryAddr.py` 的 **文本**，由 `dist/converter/memory_map_parser.js` 从 PyPTO 生成的 IR 中解析 MemRef 地址、大小、内存空间和生命周期。它不读取 GM 内存可视化的 `memory_usage_visualization.json`，也不读取普通 Python 文件。`dist/converter/memory_map.d.ts` 的解析结果有 `functions[].boxes[]`，每个 box 包含 `space`、`offset`、`size`、`start`、`end` 等供绘图使用；这是插件内部结构，不是用户需预先写出的 JSON。

## Serving Strace

`serving-strace-swimlane.json` 通过文件名被识别为独立 Serving 泳道。它是 trace 事件输入，顶层以 `traceEvents[]` 供泳道处理；事件可通过 `cat: "strace.host"` 被 `dist/process.js` 识别。基本时长事件使用 `ph: "X"`、`name`、`pid`、`tid`、`ts`、`dur`；进程/线程元数据用于 `WorkerProcess` 分组。它不要求同目录 `deps.json`、`name_map*.json`，也不应和 `chip_swimlane_records.json` 的 cycle 元组混用。
