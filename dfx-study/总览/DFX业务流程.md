# DFX 总览：设计逻辑、组件与运行流程

## 1. DFX 概述

### 1.1 DFX 是什么

广义的 DFX（**Design for X**）是一种设计理念，指在系统设计时围绕可靠性、可测试性、可服务性等质量属性建设相应能力。

在 simpler 中，DFX 是运行诊断与性能观测的能力集合：Host、AICPU 和 AICore 在各自位置记录运行信息，离线工具再将这些记录整理为阶段耗时、任务时间线、依赖关系和资源等直观视图。

### 1.2 定位与目标：DFX 要解决什么问题

DFX 主要用于定位运行错误和性能问题，帮助开发者找到相关阶段或任务、分析原因，并确定优化或修复方向。

## 2. DFX 的设计逻辑

DFX 子系统的设计与运行主要遵循以下原则：

- **由需求驱动设计。** 有明确的诊断需求时，再设计并实现对应的 DFX 子系统，并由需求确定其职责、采集内容和分析方式。
- **保证记录可信，控制观测扰动。** 采集应尽量保持原有执行逻辑和结果，避免额外开销使性能数据偏离。记录还应能归属到具体运行，并说明采集条件、缺失或丢弃情况。
- **与主运行流程相对独立。** DFX 的实现应尽量与主流程解耦：关闭专项采集时，主流程照常运行；开启后，应能区分运行失败与采集失败。运行时保留必要事实，复杂的关联和统计放到运行之后。

## 3. 整体架构与运行流程

### 3.1 组件与职责

按记录从产生到使用的路径，DFX 可分为数据采集层、数据归档层和数据分析层：采集层留下运行事实，归档层汇集记录并形成产物，分析层读取产物生成诊断视图。

**数据采集层。** Host、AICPU 和 AICore 在各自掌握事实的位置记录信息。采集模块按诊断问题分工：

| 诊断场景 | 要回答的问题 | 采集组件 |
| -------- | ------------ | -------- |
| 运行失败、卡住或出现告警 | 哪一层报告了什么错误，发生时有什么上下文？ | 日志系统记录 Host 和设备侧的状态、告警与错误。 |
| 用例或整轮运行变慢 | 时间主要增加在哪个阶段？ | STRACE 记录 Host 阶段，Device phases 记录设备阶段。 |
| 算子性能或调度出现异常 | 任务何时下发、执行，哪里出现等待？等待是否由依赖造成？ | Chip Swimlane 记录任务和调度时间；dep_gen 记录任务依赖。 |
| 需要了解 AICore 任务的硬件行为 | 流水线、访存、缓存或资源冲突等硬件事件表现如何？ | PMU 按任务采集所选事件组的硬件计数。 |
| 运行中出现资源压力 | 哪个范围的资源用量达到高水位？ | Scope Stats 记录支持的运行模式下各 scope 的资源峰值。 |
| 运行报错或结果不对，怀疑参数或张量 | 任务实际收到什么输入，产生什么输出？ | Args Dump 记录所选任务的张量输入、输出和标量参数。 |

**数据归档层。** 不同采集模块通过各自路径形成可供后续读取的产物：

- **数据交接公共框架（Profiling Framework）：** 管理持续产生的设备记录所用的缓冲、Host 接收、缓冲回收和背压，供 Chip Swimlane、PMU、Args Dump、Scope Stats 及设备侧构图时的 dep_gen 共用。它负责交接记录，不解释记录内容。
- **产物整理与落盘（各模块的 Host Collector）：** 按记录类型和运行归属整理数据并导出文件。默认模式在本轮结束时完成导出；启用 `collect_across_runs` 后，支持跨轮保留的 Collector 可在下一轮设备运行期间后台发布本轮文件。

Host 日志直接输出；Device phases 的固定时间槽由 Host 读回后写入阶段标记；Host 构图依赖直接形成依赖产物。这些路径不经过公共 Collector。

**数据分析层。** simpler 的离线工具读取日志和模块产物，关联运行、任务及时间信息，生成阶段耗时、任务时间线、依赖关系等结果；Core Swimlane 可对单任务做模拟重放。PyPTO 3.0 IDE 可直接打开芯片泳道原始记录，并读取依赖图等关联产物；当前产物的完整兼容性仍需按输入 schema 核对。具体处理方式见第 4 节。

### 3.2 从触发到结论的流程

1. **配置 DFX。** 根据要排查的问题，确定日志级别、本轮启用的采集模块和输出位置；需要跨轮后台导出时，在 Worker 初始化时启用 `collect_across_runs`。
2. **初始化采集。** 运行开始前校验配置，按需准备各模块的采集状态、设备缓冲和 Host 接收端。
3. **运行并记录。** 主流程执行时，Host、AICPU 和 AICore 在各自负责的位置记录阶段、任务、状态或参数等信息（DFX子系统）。
4. **交接并保存。** 日志按各自通道输出；持续产生的设备记录经公共框架交给 Host，由对应模块整理和保存。
5. **关闭本轮采集窗口。** 启用采集的运行按各自的运行标识归属记录。设备执行结束后，Host 读回固定阶段记录，相关模块关闭本轮采集窗口。默认模式在 `run()` 返回前排空、核对并完成应有产物的导出；跨轮模式下，支持跨轮保留的模块可在下一轮设备运行期间后台发布本轮文件，因此 `run()` 返回时文件可能尚未完成。
6. **确认产物并分析。** 跨轮模式在读取产物前调用 `Worker.flush_diagnostics()`，确认此前已关闭的各轮产物完成发布；随后用离线工具将日志和产物整理成阶段耗时、任务时间线等视图。

## 4. 产物处理与查看

### 4.1 仓库自有工具

`simpler_setup/tools/` 中的脚本用于处理已保存的日志和产物，便于按需调整，也适合临时分析：

- **阶段耗时：** `strace_timing.py`、`hbg_bind_phases`、`phase_time_split.py`。
- **任务时间线与性能分析：** `swimlane_converter.py`、`sched_overhead_analysis.py`、`critical_path.py`。
- **依赖关系：** `deps_viewer.py`、`wait_reduction_sim.py`。
- **参数与核内重放：** `dump_viewer.py`、`core_swimlane.py`。
- **资源统计：** `scope_stats_plot.py`。PMU 产物可直接查看 `pmu.csv`。

### 4.2 IDE 插件

PyPTO3 Toolkit 是 VS Code 插件，可直接打开 `chip_swimlane_records.json`，并结合 `deps.json`、`name_map*.json` 查看任务详情、依赖与函数名；也可单独打开依赖图和编译 Pass 快照。当前 simpler 导出的 `scheduler_tasks`、`scheduler_records` 和 `run_epoch` 与本机安装包的部分旧解析字段仍有差异，不能把“能打开”当作全部调度视图正确的证明。插件模块和文件结构见[PyPTO 3.0 IDE 学习](../IDE/目录.md)；离线转换到 `merged_swimlane.json` 的路径见[DFX 框架总览](DFX框架总览.md)。
